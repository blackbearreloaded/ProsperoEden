# PS5 firmware 7.40: every game session ended at its first draw

Tested on a retail PS5 on firmware 7.40 (sdk_version 0x07400006), jailbroken with the Relapse
chain, etaHEN 2.5B with its bundled kstuff, ShadowMountPlus 1.7beta4, ProsperoEden v1.000.070
installed in `/data/homebrew/PPSA99008`. Keys and firmware 20.2.0 dumped from the owner's own
console. Two games tried: a large open-world title and a small 2D one. Both behaved the same.

## Update: the real cause is kstuff being paused

Later testing on the same console showed that the firmware is not what refuses executable memory.
ShadowMountPlus pauses kstuff about 15 seconds after any title launches
(`kstuff_game_auto_toggle`, on by default), and kstuff is what makes `mprotect(PROT_EXEC)` work on
7.x. Every executable-memory request after the pause fails, which is the `can't protect` a few
seconds into a game. With kstuff kept running, even v1.000.080 (before the change below) runs on
7.40. Details: #37.

**For users:** keep kstuff running while ProsperoEden is open. Add this line to
`/data/shadowmount/config.ini` (ShadowMountPlus reloads it by itself):

```
kstuff_no_pause=PPSA99008
```

If you use etaHEN's "Pause Kstuff on Game Launch" option instead, turn it off. The sections below
describe what was measured with the pause active, and the interpreter fallback still covers
consoles where kstuff gets paused.

## Symptom

- Vulkan: `[ProsperoEden] GPU worker: can't protect` followed by
  `session failed: Rendering failed: can't protect` a few seconds after `game loaded`.
- OpenGL: the same line, after which the guest panics with result 2010-0212
  (`sf::InvalidCmifOutHeader`) while the emulator is tearing services down. The 2010-0212 report
  is a consequence, not the cause.
- v1.000.040 shows it most cleanly: no guest panic at all, only `can't protect`.

## Cause

`can't protect` is xbyak's `ERR_CANT_PROTECT`. The GPU macro JIT (`video_core/macro.cpp`,
`MacroJITx64Impl`) builds its code buffer with xbyak's default allocator and then calls
`setProtectMode(PROTECT_RW)` / `setProtectMode(PROTECT_RE)` around each compile. On this
firmware, `mprotect(PROT_READ | PROT_EXEC)` on that memory fails for an app that is not
jailbroken, so the first macro compile throws on the GPU worker and the session ends.

The CPU JIT survives because `EdenJitAllocator` gives dynarmic separate RW and RX views and the
port's `BlockOfCode` never changes page permissions. The macro JIT was the one remaining
executable-memory user on the mprotect path.

Jailbreaking the app (etaHEN's app-jailbreak list, or its legacy command server's `JAILBREAK_CMD`)
makes `mprotect` succeed but breaks the other path: `MapExecutableAlias` then fails with
`EACCES` (`EDEN_JIT_ALIAS ... active=0 errno=13`), the CPU JIT falls back to its W^X mode, and
the large title aborts right after `EDEN_JIT_FEATURES`. There is no credential state on 7.40 in
which both executable-memory paths work, so the fix has to remove one of them.

## Change

`headless/macro_recovery.cmake`: `MacroEngine::Compile` returns the interpreter on the PS5
build. The macros that matter are HLE'd already; the remainder run through
`MacroInterpreterImpl`, which needs no executable memory. The app runs un-jailbroken, as released.
Measured: the open-world title holds its native 30 fps cap at 1x with the default settings.

A first attempt instead passed `EdenJitAllocator()` to the macro JIT's `CodeGenerator` and removed
the two `setProtectMode` calls. It built, but the resulting app crashed in `BlockOfCode`'s
constructor on every launch (SIGSEGV in `Xbyak::CodeGenerator::opJmp`, fault address 0x3f: the
first code bytes written through a null `writeTop_`). Not investigated further once the
interpreter route worked; noted in case someone wants the JIT back on this firmware.

## Build on a GitHub-hosted runner (ubuntu-24.04)

`.github/workflows/build-fw740.yml` builds the package with `make package` on `ubuntu-24.04`.
Differences from the documented Ubuntu 26.04 host that needed handling:

- `meson` 1.3.2 from apt is too old for the pinned Mesa (needs >= 1.4): installed from pip.
- Mesa's `mesa_clc` host build needs `llvm-18-dev libclang-18-dev libclang-cpp18-dev
  libllvmspirvlib-18-dev libclc-18-dev spirv-tools spirv-headers`.
- lld 18 exports undefined weak symbols from executables; lld 21+ does not (`-z
  dynamic-undefined-weak` opts back in). Mesa's entrypoint tables reference thousands of optional
  driver entrypoints as weak symbols (`radv_*`, `wsi_*`, `vk_common_*`, ...), and the native
  packager rejects any dynamic import without an SDK stub
  (`no public SDK stub exports required symbol radv_EnumeratePhysicalDevices`). lld 18's only
  switch for this is `--no-dynamic-linker`, which in that version affects nothing else in this link
  (no PT_INTERP in `ps5-pie.ld`). `tools/link-headless-native.sh` passes it; on lld 21+ it is
  redundant.
- `actions/cache` on `~/.cache`, `.deps` and the sibling checkouts brings a rebuild down from
  about 50 minutes to about 12.
